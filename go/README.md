# Go-версия блога

Рабочий этап переноса `vas3k.blog` на Go. Python-приложение в корне сохранено для сверки. Это ещё не замена всего исходного движка: точный статус — в [PARITY.md](PARITY.md).

Go 1.26 (toolchain скачивается автоматически), PostgreSQL 17, серверные HTML-шаблоны. Для чтения, редактирования и комментариев JavaScript не требуется. Вход администратора с Passkey использует браузерный WebAuthn API и требует JavaScript.

## Локальный запуск

Из каталога `go/` создайте защищённый, неотслеживаемый файл окружения:

```sh
umask 077
python3 - <<'PY'
import secrets
from pathlib import Path
password = secrets.token_hex(32)
with Path('.env').open('x') as f:
    f.write('POSTGRES_PASSWORD=' + password + '\n')
    f.write('DATABASE_URL=postgres://blog:' + password + '@127.0.0.1:55432/blog?sslmode=disable\n')
    f.write('BASE_URL=http://localhost:8080\n')
    f.write('LISTEN_ADDR=127.0.0.1:8080\n')
PY
set -a
. ./.env
set +a
docker compose up -d --wait
go run ./cmd/blog migrate
```

Запустите приложение:

```sh
export OWNER_EMAIL='you@example.com'
go run ./cmd/blog serve
```

Посетители входят через IndieAuth на `/login/`. Вход администратора — отдельно на `/admin`, только через **Passkey** (Touch ID, телефон или аппаратный ключ). Парольных HTTP-маршрутов нет; редактор остаётся на `/godmode/`.

В локальном предпросмотре откройте `/admin`: пока в базе нет ключей, показана кнопка «Зарегистрировать первый ключ». Она сразу запускает регистрацию Passkey, если запрос пришёл напрямую с loopback, сервер слушает loopback, `BASE_URL` — HTTP localhost и задан `OWNER_EMAIL`. После регистрации появляется «Войти с ключом». Проверка отсутствия ключей повторяется при завершении под блокировкой; устаревшая вторая вкладка не может добавить ещё один первый ключ.

Для публичного домена, работы через прокси и восстановления доступа остаётся `tools/create-local-admin.command` (для текущего локального предпросмотра) или команда `admin-setup` на нужном сервере. Скрипт подготовит учётную запись `niko@antiit.ru` и откроет одноразовую страницу регистрации ключа в браузере. Создание Passkey нужно подтвердить лично на своём устройстве. Существующие ключи сохраняются. Скрипт использует только локальную базу `blog_test` на `127.0.0.1:55432` и не печатает ссылку настройки.

Для другого окружения выполните на сервере в отдельном терминале, с загруженными `DATABASE_URL` и `BASE_URL`:

```sh
export OWNER_EMAIL='you@example.com'
export OWNER_NAME='Автор'
setup_dir=$(mktemp -d)
export ADMIN_SETUP_FILE="$setup_dir/setup.url"
go run ./cmd/blog admin-setup
```

Команда записывает одноразовый URL в файл с правами 0600; откройте его в своём браузере через защищённый локальный доступ и удалите файл после использования. Не отправляйте ссылку в чаты или логи. Для первого ключа на публичном домене и восстановления доступа требуется эта команда на сервере. Ссылка действует 15 минут, разрешает зарегистрировать один ключ и сама не создаёт сессию. Повторная команда отзывает предыдущие ссылки; не повышает роль существующих обычных пользователей.

Для демонстрационных записей, только по желанию:

```sh
go run ./cmd/blog import < examples/posts.json
```

`BASE_URL` — точный внешний origin, без пути. Он участвует в проверке Origin/CSRF и генерации ссылок. `BLOG_TITLE`, `BLOG_AUTHOR`, `BLOG_LANGUAGE` задают название, автора и язык по умолчанию. Язык конкретной страницы выбирается через `?lang=ru`; дата в редакторе указывается в UTC. За reverse proxy нужно сохранить внешний Origin; `BASE_URL` в production должен использовать HTTPS. Заголовок X-Forwarded-For намеренно не считается доверенным: текущие лимиты по IP за прокси общие для его адреса.

## Что работает

- Публикации, разделы, пагинация, переводы, отдельный CSS, обложки и внешние ссылки.
- Черновики, отложенная публикация, закрытые записи, флаг главной страницы и отключение комментариев.
- Вход посетителей через IndieAuth, администратора — через Passkey на `/admin`; сессии и профили в PostgreSQL.
- Комментарии, ответы, привязка к фрагментам, закрепление и удаление; атомарная защита от повторного голоса.
- Markdown, GFM, сноски, многострочные `[[[ … ]]]` и `{{{ … }}}`, цитаты `% `, спойлеры `[? … ?]`, изображения, MP4/WebM и YouTube.
- Поиск в открытом содержимом, RSS, JSON Feed, sitemap, совместимость с адресами `index.html` и сменой раздела.
- Подтверждённая email-подписка, отписка, очередь анонсов с повторными попытками.
- Разметка `h-card`, `h-entry`, `h-feed`. Поддерживаются Webmention, IndieAuth и Micropub; настройка и ограничения описаны ниже.

HTML публикаций проходит очистку; авторские скрипты выполняются в отдельных блоках `embed`, а внешние iframe изолируются через sandbox. Комментарии не принимают HTML. Inline-обсуждения сейчас собраны под статьёй со ссылкой на фрагмент; отображение обсуждения непосредственно внутри текста ещё предстоит перенести.

## Шпаргалка по разметке

`examples/formatting.md` — демонстрационная статья с синтаксисом и живыми примерами. Импортировать её можно отдельно, не изменяя другие записи:

```sh
python3 tools/demo_post.py | go run ./cmd/blog import
```

Адрес: `/blog/vozmozhnosti-oformleniya/?lang=ru`. Обложка и короткий видеопример входят в бинарник; внешние медиа для демонстрации не нужны. Повторный импорт обновит только эту демонстрационную запись.

## Форматы для машинного чтения

- `/{kind}/{slug}/index.md?lang=ru`: обычный Markdown с названием, автором, датами, языком, обложкой и канонической ссылкой. Получается из того же очищенного содержимого, что и HTML. Внутренние контейнеры преобразуются, ссылки на обсуждение удаляются, видео представлены ссылками. Спойлеры и раскрывающиеся блоки экспортируются вместе с текстом.
- `/llms.txt?lang=ru`: краткое описание блога, архив, ленты, карта сайта и 20 последних открытых записей со ссылками на Markdown. Выбор языка использует тот же параметр, что и страницы.
- Открытые опубликованные записи содержат JSON-LD `BlogPosting`: название, описание, автор, даты, язык, обложка и канонический URL. HTML и HTTP Link сообщают адрес Markdown; `rel=describedby` ведёт к llms.txt.

Публичный путеводитель никогда не включает черновики, будущие или закрытые записи, даже при запросе владельца. Markdown использует те же права доступа, что и статья: участник может читать закрытые записи, владелец — предпросмотр. Такие ответы помечены noindex, все ответы остаются private/no-store. JSON-LD не добавляется в закрытые записи и предпросмотр.

## Оформление

Стили в `internal/blog/static/css/` и шрифты Ubuntu/Merriweather перенесены из исходного `frontend/static/`. `site.css` содержит адаптацию к Go-шаблонам: карточки с обложками, текстовые карточки без изображений, заголовки статей, блоки текста, комментарии и формы. Используется только исходная тёмная палитра, независимо от настроек системы и старого сохранённого выбора. Светлая тема и переключатель удалены. `navigation.js` управляет мобильным меню и раскрытием поиска; без JavaScript ссылки меню остаются доступны. В верхнем меню — «Статьи» и «Заметки»; ссылки на путешествия и email-подписку убраны. Поиск и вход оформлены круглыми кнопками 🔍 и 👤, как в исходнике; поле поиска раскрывается под шапкой на любой странице. Шапка, поиск, основной контейнер и футер используют общую ширину до 1000 px и одинаковые боковые отступы (20 px, на мобильных 15 px). Внутренние колонки текста и форм остаются уже. На первой странице главной после первой записи размещена карточка автора с h-card и rel="me". Её текст и ссылки редактируются в `internal/blog/templates/about.html`; они основаны на публичном профиле NikoVonLas в GitHub. Карточка остаётся доступной и при пустой ленте. Чужие имя, аватар и контакты не переносятся. Точная композиция исходной главной и индивидуальные legacy-настройки записей остаются в матрице переноса.

## Рассылка

По умолчанию отправка выключена. Для включения нужны `SMTP_ADDR=host:port`, `MAIL_FROM`, при необходимости `SMTP_USER` и `SMTP_PASSWORD` через защищённое окружение. Удалённый SMTP должен поддерживать STARTTLS; обычное соединение разрешено только на localhost для локального тестового приёмника. Implicit TLS на порту 465 пока не поддерживается.

Кнопка «Отправить подписчикам» ставит анонс открытой опубликованной записи в очередь. Задачи сохраняются в БД, повторная постановка того же анонса одному подписчику не создаёт дубликат. SMTP даёт доставку как минимум один раз: при аварии между принятием письма сервером и записью результата возможен повтор. Message-ID остаётся прежним. После 8 неудачных попыток задача остаётся в outbox для диагностики. Никаких внешних писем интеграционные тесты не отправляют.

## Импорт и резервные копии

`GET /godmode/export/` экспортирует **публикации**, включая черновики, в JSON. Команда `import` проверяет записи и применяет весь набор одной транзакцией; конфликт откатывает весь импорт. ID сохраняются, повторный импорт обновляет записи по ID. Медиа остаются URL: файлы не скачиваются автоматически.

Для экспорта публикаций из Django:

```sh
# Выполняется в настроенном Python-окружении исходного движка.
python manage.py dumpdata posts.Post --indent 2 > posts.django.json
python3 go/tools/convert_django.py < posts.django.json > posts.go.json
# Затем из go/ с настроенным DATABASE_URL:
go run ./cmd/blog import < ../posts.go.json
```

JSON записей не является полным бэкапом сайта. До миграции существующего сайта нужно отдельно перенести пользователей, комментарии, реакции, подписки и файлы. Для полного бэкапа новой версии используйте `pg_dump` и резервную копию своего медиахранилища. В дампе есть чувствительные данные, поэтому храните его вне Git с ограниченным доступом.

## Проверки

```sh
go test -race ./...
go vet ./...
TEST_DATABASE_URL='postgres://…/blog_test?sslmode=disable' go test -race ./...
```

Без `TEST_DATABASE_URL` интеграционные тесты пропускаются. С ней каждый запуск создаёт собственную случайную PostgreSQL-схему и удаляет только её. Используйте отдельную тестовую БД. Тесты проверяют маршруты, закрытые записи, черновики, CSRF, редактор, комментарии, конкурентные голоса, очередь подписок и сохранение сессии после перезапуска приложения.

Docker-образ собирается командой `docker build -t blog-go .`. Миграции запускаются отдельно: `blog migrate`; сервер — `blog serve`. Бинарник работает от непривилегированного пользователя. `compose.yaml` предназначен для локальной БД, не является production-деплоем.

## Происхождение

Исходник: `vas3k/vas3k.blog`, ревизия `fcf4fd7c4bc02ec5ef905a7487e93933b8cbe9ea`. Новая версия находится в отдельном каталоге и использует новые Go-шаблоны. В исходном репозитории не обнаружена общая лицензия проекта; лицензии его сторонних ресурсов нельзя трактовать как лицензию всего движка. Условия дальнейшего распространения исходных ресурсов остаются открытым вопросом.

### Богатый контент и загрузки

- Главная: последняя опубликованная статья (`blog`) выбранного языка, карточка автора, затем статьи и заметки по убыванию даты без повтора верхней статьи. Верхняя статья выбирается независимо от «На главной»; остальные записи учитывают этот флаг. Черновики и будущие публикации не попадают в ленту. Статьи занимают всю ширину, соседние заметки — по две на больших экранах, все карточки — по одной на мобильных. Карточка автора и верхняя статья не повторяются при пагинации.
- Блоки `mermaid` отображаются через локальную Mermaid 12.2.0 (`look: handDrawn`, тёмная тема); неподдерживающие этот вид типы используют оформление Mermaid. Код подсвечивает highlight.js 11.12.0. В спойлерах работает вложенное Markdown-оформление.
- Блок `embed` запускает авторский HTML со скриптами в отдельном iframe. Документ выдаётся через маршрут `/embeds/{id}/{digest}/document` с проверкой доступа к статье и CSP sandbox без `allow-same-origin`. На самой странице исполняемый HTML удаляется. Произвольные HTTP/HTTPS iframe тоже изолируются; запрет встраивания со стороны провайдера не обходится.
- Превью URL: кнопка в редакторе получает Open Graph/title/description, создаёт HTML-карточку и вставляет её в текст. Данные фиксируются на момент вставки. Загрузчик проверяет публичность адресов, повторяет проверку после редиректов, закрепляет проверенный IP при соединении, ограничивает время и размер ответа. Внутренние сети и нестандартные порты недоступны.
- Изображения в тексте, обложка и аватар загружаются через `POST /uploads/` с сессией и CSRF. Для картинок записи нужен администратор, для аватара — обычный вход. JPEG/PNG/GIF/WebP до 10 МБ и 24 Мп; SVG не принимается. Файлы сохраняются в таблице `uploads`, поэтому входят в резервную копию PostgreSQL. `/media/{id}` — неизменяемый публичный адрес с кэшированием; изображения закрытых записей также доступны по прямой непредсказуемой ссылке. Экспорт публикаций JSON не включает байты файлов — для полного переноса нужна копия базы.
- JavaScript-сборка: `cd web && npm ci --ignore-scripts && npm run build`. Версии и lockfile зафиксированы, готовые ресурсы в `internal/blog/static/vendor/` включены в Go-бинарник; для обычной Go-сборки Node.js не требуется.

### Карточка автора

В админке `/godmode/` откройте «Карточка „Обо мне“» (`/godmode/about/`). Администратор также видит ссылку редактирования на самой карточке. Доступны имя, ник, описание в Markdown, фотография с загрузкой и до 12 ссылок; флаг «Мой профиль» добавляет `rel=me`. Изменения сразу видны на первой странице главной. Пустой адрес фото убирает фотографию, пустые строки ссылок не сохраняются. Личный профиль пользователя и подпись автора публикаций настраиваются отдельно.

Карточка хранится в `settings.about_card` в PostgreSQL; до первого сохранения используется исходное содержимое. Она входит в резервную копию базы, но не в JSON-экспорт публикаций. Сохранение из устаревшей вкладки не перезаписывает новые изменения; форма сохраняет введённый текст для ручного переноса.

### Webmention

Блок «На других сайтах» отображается только при наличии одобренных упоминаний.

Реализован приём и отправка [Webmention](https://www.w3.org/TR/webmention/). Перед обновлением приложения выполните `blog migrate` (схема 3). Фоновая проверка/отправка запускается вместе с `blog serve`; отдельный сервис не нужен.

- Открытые опубликованные записи с включёнными комментариями объявляют `/webmention` через HTML и HTTP `Link`. Закрытые записи, черновики, будущие публикации и записи-переадресации не принимают упоминания.
- `POST /webmention` принимает `application/x-www-form-urlencoded` с `source` и `target`, возвращает `202`, затем проверяет источник в очереди PostgreSQL. Это публичный протокольный endpoint без пользовательской сессии; все административные действия по-прежнему требуют входа и CSRF.
- Проверяется точная ссылка на `target` в HTML, включая фрагмент; относительные ссылки разрешаются с учётом конечного URL и HTML base. JSON/plain text источники пока не поддерживаются. Сохраняются название страницы и тип связи (`u-in-reply-to`, `u-like-of`, `u-repost-of` или обычное упоминание); полный чужой текст и фотографии не копируются.
- В редакторе есть раздел `/godmode/webmentions/`: публикация, скрытие, повторная проверка и состояния исходящих уведомлений. Только проверенные и одобренные ссылки появляются в блоке «На других сайтах». Изменение отображаемых данных возвращает упоминание на модерацию; удаление ссылки или ответ 404/410 скрывает его. Повторы не создают дубликаты. Периодическая перепроверка пока не включена: она выполняется по новому уведомлению либо вручную.
- В редакторе сохранённой записи кнопка «Отправить Webmention» ставит в очередь внешние ссылки из её текста, а также ранее отправленные адреса, даже если ссылка убрана. После правки текста сохраните запись и нажмите кнопку снова. Автоматической отправки при сохранении или отложенной публикации нет. До 100 текущих ссылок и 300 адресов с учётом истории; ссылки из меню, комментариев, исполняемых embed-блоков и URL изображений не отправляются.
- Endpoint получателя обнаруживается по HTTP Link, затем HTML link/a, включая относительные адреса и query-параметры. Отправляется POST с source/target; любой 2xx считается успехом. Очередь повторяет временные ошибки до пяти попыток. Перед отправкой повторно проверяются публичность и адрес записи; закрытие записи или изменение её адреса отменяет старую отправку (автоматические tombstone-уведомления пока не поддерживаются).
- Все внешние загрузки и отправки ограничены публичными HTTP/HTTPS-адресами на портах 80/443: проверяется каждый DNS-адрес и редирект, соединение устанавливается с проверенным IP, системный HTTP proxy не используется. Лимит ответа — 2 МБ, таймаут запроса — 8 секунд, до четырёх переходов. Входящие запросы ограничены по IP, домену источника и общему числу.

Для реального обмена нужен публичный домен в `BASE_URL`: другие сайты не смогут проверить страницу на localhost. Разработка проверяется изолированными HTTP-ответами и тестовой базой; полная внешняя проверка через webmention.rocks возможна после публикации сайта. Тесты не отправляют уведомления реальным сайтам.

### IndieAuth и Micropub

Сначала выполните `blog migrate` (схема 6). Для работы с интернет-редакторами нужен публичный HTTPS `BASE_URL`; `localhost` предназначен только для разработки. Сервер реализует роль **IndieAuth provider** для владельца и **IndieAuth client** для входа посетителей по адресам их сайтов. В совместимом редакторе укажите корень блога (`https://your-blog.example/`), войдите администратором через Passkey на `/admin` и подтвердите нужные разрешения. Регистрация приложений и отдельные пароли не нужны.

- Discovery: HTML-ссылки и HTTP `Link` на главной; `/.well-known/oauth-authorization-server`, `/indieauth/auth`, `/indieauth/token`, `/micropub`.
- Обязателен PKCE **S256**. Запрос согласия привязан к текущей сессии и действует 10 минут; одноразовый код — 5 минут. Доступ выдаётся на 30 дней, без refresh token. В базе хранятся хэши кодов/токенов. После истечения подключите приложение заново.
- Разрешения: `create`, `update`, `delete`, `undelete`, `media`, `read`, `profile`. `update` также разрешает чтение исходников; `create` — загрузку изображений. `read`/`update` открывают исходники **всех** записей владельца, включая черновики и закрытые. `profile` отдаёт имя и фото из карточки автора, без email. Можно подтвердить только часть запрошенных прав.
- `/godmode/apps/` показывает действующие подключения и позволяет немедленно отозвать отдельный токен. API отзыва: `POST /indieauth/revoke` с form-полем `token`; совместимый старый вариант — `/indieauth/token` с `action=revoke`. Токены заблокированного или лишённого роли администратора пользователя перестают работать.
- Callback допускается на том же origin, что `client_id`, либо по точному совпадению с опубликованным `redirect_uris` в JSON metadata или `rel=redirect_uri` в HTML/HTTP Link. Поддерживаются HTTP/HTTPS callback, **не** custom schemes. Loopback client URL никогда не загружается сервером; внешние metadata проходят SSRF-проверки.
- Identity-only flow без scope возвращает `me` через `POST /indieauth/auth`, но не выдаёт access token. `GET /indieauth/token` с Bearer возвращает сведения о своём токене. `/indieauth/introspect` требует Bearer и ограничен токенами того же пользователя и приложения; это не универсальный endpoint для сторонних resource servers.

Micropub принимает Bearer в заголовке `Authorization` или поле `access_token` form/multipart POST; query-string токены и cookie-сессии не авторизуют API. Поддерживается CORS для браузерных клиентов без cookie credentials.

- Создание `h-entry`: form-urlencoded, JSON или multipart с текстовыми полями. Запись с `name` становится статьёй, без заголовка — заметкой. Адрес генерируется автоматически; `mp-slug` задаёт свой адрес при создании. Неизвестные свойства игнорируются; токен не попадает в запись.
- Поля: `name`, `summary`, `content`, `published` (RFC3339), `category`, `photo` (URL или `{value, alt}`), `featured` (обложка), `in-reply-to`, `like-of`, `repost-of`, `bookmark-of`, `syndication`. Ссылки/фото/теги отображаются в записи, RSS, JSON Feed и Markdown-экспорте. Ответы, лайки и закладки остаются в ленте заметок. Вложенные microformats-объекты не поддерживаются.
- Строковый `content` — обычный текст, не Markdown. `{ "html": "..." }` проходит очистку HTML: скрипты и iframe из внешнего редактора не исполняются. Встроенный редактор по-прежнему поддерживает Markdown и свои sandbox embed-блоки.
- `post-status=draft` создаёт черновик; `published` публикует. Будущая дата откладывает появление на сайте. `visibility=private` соответствует «Только участникам», `public` — открытой записи. Остальные значения отвергаются.
- Обновление: JSON `action=update`, `url`, операции `replace`, `add`, `delete` (список свойств или конкретные значения). Изменение заголовка не меняет URL; смена slug/kind/lang через Micropub не поддерживается. Правки выполняются под блокировкой строки. `q=source&url=...` возвращает актуальные свойства, в том числе после правок встроенным редактором; доступны `properties[]` для выбора полей.
- `action=delete` — мягкое удаление: запись пропадает из публичных страниц, поиска, фидов, карты сайта и Markdown. Текст и комментарии сохраняются; `action=undelete` восстанавливает прежние настройки публикации. В админке запись помечена «В корзине». Восстановление выполняется через Micropub.
- `q=config` объявляет `/micropub/media`; `q=syndicate-to` возвращает подключённый Telegram-канал. При создании записи `mp-syndicate-to` (массив URL в JSON или `mp-syndicate-to[]` в форме) ставит копию в очередь POSSE атомарно с сохранением. Поддерживается только немедленно опубликованная открытая запись; для черновика, будущей даты или неизвестной площадки — 400 без сохранения. При обновлении записи эта команда не выполняется; для существующей записи используйте предпросмотр POSSE в редакторе. Автоматической отправки Webmention/писем через Micropub нет; используйте существующие кнопки редактора.
- Media endpoint: multipart с одним полем `file`, JPEG/PNG/GIF/WebP до 10 МиБ и 24 мегапикселей. Возвращает `201` и абсолютный URL в `Location`; используйте его в `photo`/`featured`. Загрузка бинарных файлов непосредственно в `/micropub` не поддерживается. Изображения доступны по прямому адресу независимо от приватности записи.

Проверено локальными интеграционными тестами, включая одноразовое конкурентное погашение кодов, PKCE/CSRF, границы прав, отзыв, создание/обновление/восстановление и изображения. Проверки `indieauth.rocks`/`micropub.rocks` и подключение реального интернет-клиента ещё требуют публичного HTTPS-домена. Спецификации: [IndieAuth](https://indieauth.spec.indieweb.org/), [Micropub](https://www.w3.org/TR/micropub/).


### Вход посетителей через свой сайт

На `/login/` посетитель указывает URL сайта с IndieAuth, подтверждает вход у своего провайдера и возвращается к исходной записи. Можно вводить домен без `https://`. Почта и пароль блогу не передаются. Вход владельца расположен отдельно на `/admin` и использует только Passkey.

- Discovery поддерживает `rel=indieauth-metadata` (HTTP Link и HTML link) и старый `rel=authorization_endpoint`. Метаданные имеют приоритет; некорректные метаданные не вызывают откат к старому протоколу. Endpoint входа должен быть HTTPS; профиль — HTTP/HTTPS без порта, IP-адреса, фрагмента и credentials. Локальные адреса недоступны, в том числе после DNS и редиректов.
- Клиент объявлен в `/indieauth/client`; callback — `/login/indieauth/callback/`. Используются PKCE S256, одноразовый state и отдельная HttpOnly/SameSite=Lax cookie с привязкой к браузеру на 10 минут. Для современного discovery проверяется `iss`. Обмен кода выполняется без редиректов; возвращённый `me` повторно проверяется через discovery.
- Запрашивается только `profile` (имя/фото). Access token не нужен и не сохраняется. В базе — хэши state и browser nonce; PKCE verifier вычисляется через HMAC из серверного секрета и state. Завершённые попытки удаляются сразу, истёкшие — при следующем начале входа.
- Аккаунт связан только с подтверждённым URL `me`, без объединения по email или имени. Имя и аватар можно изменить в `/profile/`; ссылка на подтверждённый сайт появляется у комментария. Повторный вход сохраняет правки профиля.
- Новый посетитель может комментировать открытые записи, но не получает членство, закрытый RSS или доступ в редактор/Micropub. Существующие локальные участники сохраняют свои права. Блокировка пользователя запрещает и текущие сессии, и новый вход.
- Проверки выполнялись с тестовым провайдером. Для реального обмена с внешними провайдерами нужен публичный HTTPS `BASE_URL`; localhost предназначен для разработки. OpenID Connect не подключён.


### Passkey администратора

- Перед обновлением выполните `blog migrate` (схема 6). Старые парольные сессии администратора больше не принимаются. Старые поля паролей остаются в базе для совместимости миграции, но не используются для входа. Создание участников с паролем удалено; посетители регистрируются через IndieAuth. Существующие права участников в базе сохранены.
- Используется [go-webauthn](https://github.com/go-webauthn/webauthn) v0.18.2: проверка challenge, подписи, origin, RP ID и обязательного user verification. Подходят discoverable credentials (Passkey) с Touch ID/биометрией/PIN; простого касания ключа без подтверждения пользователя недостаточно.
- `BASE_URL` определяет точный разрешённый origin и домен RP ID. Production требует HTTPS; `http://localhost:8080` подходит для локального просмотра. Ключ localhost не переносится на будущий публичный домен — зарегистрируйте ключ для нового домена через серверную команду.
- Попытки входа/регистрации одноразовые, привязаны к HttpOnly cookie и действуют 5 минут. Все browser POST проходят Origin/CSRF-проверку. Приватный ключ остаётся у пользователя; сервер хранит публичный ключ, метаданные и счётчик.
- Сессия администратора действует 12 часов и привязана к конкретному ключу. В `/admin/keys` можно добавить запасной ключ и удалить старый; для изменений нужен вход не старше 10 минут. Последний ключ удалить нельзя. Удаление ключа отзывает выданные через него сессии; блокировка пользователя также закрывает доступ.
- Micropub использует отдельные выданные токены. Они сохраняют свой срок и могут быть отозваны через `/godmode/apps/`; удаление Passkey не отзывает API-токены автоматически.
- Автотесты выполняют регистрацию с CBOR-attestation и вход с ECDSA-подписью, проверяют подмену origin/RP ID, отсутствие user verification, неверную подпись, повтор/истечение попытки, одноразовые setup-ссылки, роль, блокировки, CSRF и отзыв сессий. Физический ключ и Touch ID требуют личного подтверждения владельца.


### POSSE → Telegram

В редакторе сохранённой записи нажмите **«Отправить в Telegram»**: откроется предпросмотр и кнопка публикации в канале. Статья отправляется как заголовок + описание (до 700 символов UTF-16) + ссылка; заметка — как текст + ссылка. Сообщение ограничено 4096 единицами UTF-16, ссылка всегда сохраняется. Markdown преобразуется в обычный текст; скрипты, iframe и скрытые спойлеры не копируются. Telegram может добавить превью оригинальной страницы с обложкой. Правки и удаления в блоге не меняют уже опубликованную копию.

Настройки процесса приложения:

- `TELEGRAM_CHANNEL` — публичный `@username` канала; для этого блога по умолчанию `@m1ndstr3am`.
- `TELEGRAM_BOT_TOKEN` — токен бота с правом публикации в этом канале. Передавайте через штатный механизм секретов приложения (защищённый `.env` вне Git, переменные сервиса, Docker secrets через entrypoint). Не помещайте токен в URL браузера, командную строку запуска, репозиторий или логи. Приложение читает переменную окружения, `.env` автоматически не загружает.
- `BASE_URL` — публичный HTTPS-origin блога. Пока блог доступен только на localhost, работает предпросмотр; отправка отключена, чтобы не публиковать неработающую ссылку.

После обновления выполните `blog migrate` (схема 7). Фоновый обработчик запускается вместе с `blog serve`. Без токена сайт работает как обычно, а интерфейс показывает, что канал ещё не подключён.

Очередь хранится в PostgreSQL, уникальная пара «запись + канал» предотвращает повторную публикацию. Непосредственно перед отправкой проверяются публичность записи, её версия и канал. Изменённая, закрытая, снятая с публикации или удалённая запись отменяет отправку. При успешном ответе URL сообщения сохраняется в `posts.data.posse` и показывается как `u-syndication` в HTML, Markdown, фидах и Micropub source; последующие правки записи сохраняют эту ссылку.

Telegram `sendMessage` не даёт ключа идемпотентности. При таймауте, обрыве соединения, некорректном ответе или прерывании процесса статус становится «Нужно проверить канал», без автоматического повтора. Владелец может сохранить ссылку на уже появившееся сообщение либо явно подтвердить, что сообщения нет, и повторить отправку. Только явный отказ 429 повторяется автоматически по `retry_after` (не более пяти попыток); другие явные отказы требуют ручного повтора. Тексты ошибок API и URL с токеном не записываются в логи или очередь.

Проверки используют подставной Telegram transport и отдельные схемы PostgreSQL: реальные сообщения не публикуются.

Протоколы: [Telegram sendMessage](https://core.telegram.org/bots/api#sendmessage), [Micropub syndication targets](https://www.w3.org/TR/micropub/#syndication-targets).
